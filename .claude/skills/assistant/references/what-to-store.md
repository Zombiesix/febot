# 存什么 / 怎么存

> **触发条件只有一个:用户明说「存一下 / 存进 X 仓」。**
> 助手**不自己判断该不该存、不自动入库、不事后提醒**。
> 下面两张表不是「自动扫描规则」,而是用户让存时,判断「这条值不值得存、该怎么存」的参考。

## ✅ 值得存(代码里读不出来的业务知识)

| 类别 | 判据 | 例子(某业务仓实际会遇到) |
| --- | --- | --- |
| 业务规则及**原因** | 为什么这么设计 | 「这个校验为什么放前端」 |
| 字段/命名的**业务含义** | 标识符 ≠ 字面意思 | `bizType` 实际是订单来源 |
| **命名不一致映射** | 代码名/接口名/页面名三对不上 | `catheter` ↔ `conduit-manage` ↔ 「导管管理」 |
| 状态机/流程的业务语义 | 业务态 vs 技术态 | 「出科」vs「转科患者」 |
| 角色/权限的业务含义 | 谁能做什么、为什么 | 权限码背后的角色 |
| 历史决策与坑 | 为什么不用 X | 「为什么这个组件是间接引用」 |
| 领域黑话/缩写 | 字面不可解 | `mdm`、`fdp-api`、`ai-generate` |

## ❌ 不值得存

| 类别 | 为什么 |
| --- | --- |
| 路由表 / 组件树 / API 清单 / 端点 | 每次用索引器现算,存了必过期(**铁律一**) |
| store 字段清单 / 事件清单 | 同上,属事实现算 |
| 框架用法、通用编程知识 | 不是本公司的业务 |
| **无 `evidence` 的猜测** | **直接丢弃,不许入库**,并如实告诉用户为什么没存 |

> 判据一句话:**这条会随代码变吗?** 会变 → 现算;不会变(是「为什么」)→ 可以存。

## 怎么存(实测契约,2026-10-10 坐实)

CLI 已封装,正常只需:

```
node scripts/assistant-memo.mjs retain \
  --bank assistant-<仓名> \
  --content "<业务结论,一句话说清>" \
  --repo <仓名> [--module <模块>] --evidence <文件:行> [--date <YYYY-MM-DD>]
```

用户可指定 `--repo` / `--module`;`--evidence` / `--date` 由助手补全。**缺 evidence 就不存。**

### 元数据落到哪(实测结论,别想当然)

| 通道 | 写什么 | 为什么 |
| --- | --- | --- |
| `tags` | `repo:<仓名>` · `module:<模块>` · `ev:<文件:行>` | 唯一在原始条与派生条上**都存在**、且**服务端可筛**的通道 |
| `metadata` | `{repo, module, evidence, source, date}` | 逐字存活、recall 会回传;但**只在原始条(world)上**,派生条(observation)上恒为空——所以与 tags 冗余一份 |
| `timestamp` | `--date` | 落到原生 `date` 字段,是 `list --days` 的锚点 |

> 三条容易踩的实测坑(详见 `docs/assistant-agent-实施步骤.md` 附录):
> 1. 一条 retain 会被拆成 **2 条**:原始条 + 派生条;`metadata`/`context` **只有原始条有**。
> 2. 所以出处**必须冗余写进 tags**(`ev:`),否则派生条答完答不出「凭什么这么说」。
> 3. **别把元数据塞进 `context`**——实测它时有时无,不能当存储用(原计划 §4.2 的写法已作废)。

### 存完必做

1. **回报**「已存到 `assistant-<仓名>`」,并给出落库 `id`。
2. 用户没看见也想核实 → `/assistant status` 或 `list --repo <仓名>`。
3. CLI 是**硬报错**的:报错了就是没存进去(**不是**「静默成功」),如实告诉用户存失败及原因。
