# 助手层 Agent（Claude Code 内）— 建设计划

> 目标读者：使用者本人（新进前端，懂技术不懂公司业务），以及要回答的「对外提问者」。
> 一句话：一个能在 Claude Code 里随时叫起来、**问什么答什么、说存就存**的助手——
> 帮你把业务捋清楚、把文档存下来、并用同一套东西回答别人对项目的提问。
> **它不主动、不讲解、不追问、不考试。**

---

## 0. 现状盘点：零件都有，缺的是「助手层」

**不用从零造零件，但助手层要从头写。** 现有可复用的三块：

| 已有资产                     | 是什么                                                                                                                                                                                                                                                                                                                                                                                                                                                   | 对本次的价值                                                                                                          |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `code-indexer`               | Vue3 静态索引器 **v2**。CLI 12 命令（`scan`/`map`/`trace`/`trace-event`/`trace-state`/`channels`/`modules`/`warnings`/`search`/`stats`/`rescan`/`serve`）+ **自带 stdio MCP server（9 工具）**。覆盖：路由（带中文业务名）/ 模块 / API 域 / 组件图 / **Pinia store 读写台账** / **组件 emit 事件链** / **权限码台账（标注判定在本仓还是 qiankun 宿主）** / **存储通道（localStorage/sessionStorage/cookie key 台账）** / WS 定位 / 模块间关系 / 静态告警 | **事实层**现成：解析不出的一律**带原因 + evidence** 输出，不静默丢弃——与助手「答不上就说答不上」同构。单仓扫描约 1–3s |
| `scripts/hindsight-memo.py`  | Hindsight 封装 CLI（recall/retain/reflect，**软降级**）                                                                                                                                                                                                                                                                                                                                                                                                  | **文档层**现成，API 已实测                                                                                            |
| `docs/hindsight-接入方案.md` | bank 设计、retain/recall 时点、蒸馏规则                                                                                                                                                                                                                                                                                                                                                                                                                  | 沿用其「写为什么，不写是什么」纪律                                                                                    |

> **事实层前提曾被证伪、已修复（2026-10-10）**：本计划初稿写下「事实层现成、直接用」时，
> 索引器的端点抽取器实际只覆盖 **1/11 仓**（icis 161 个），其余 10 仓**全是 0 端点且静默**——
> 助手会对新人说「这个模块没有接口」= 静默撒谎。同日完成形态补全并验收：
> **11/11 仓全部非零，端点 161 → 2624**；路由 204 → 257（带中文业务名 194）；
> store 90 个、事件边约 2500、权限码 200+、存储 key 55、WS 5 处（11 仓合计）。
> 这段历史保留的原因：**「事实层现成」这类前提必须带着验收证据，不能凭感觉写。**

**缺的是什么：**

1. **没有任何「助手层」** —— 没有服务协议（怎么答、怎么存）。这是本次的主体工作量。
2. **没有把 Hindsight 接给「助手」** —— 现有 `hindsight-memo.py` 是给需求流水线用的，没有助手侧的调用编排。
3. **没有「文件夹粒度怎么答」的约定** —— 需要定清：问某个文件夹时，助手**按需读源码**，
   而不是先跑一个批量文档化 skill。
4. **没有「存什么 / 怎么存」的约定** —— 什么时候存、存成什么形状，没有规矩。

> 与本计划边界「只读目标仓、产物只写 `docs/assistant/`」**直接冲突**；且它产出的"业务语义"是
> LLM 读码的**派生物**，会随代码过期，与铁律一（事实现算）相冲。文件夹粒度改由**助手按需 `Read`** 承担（§4.3）。
> skill 文件本身**保留**（通用工具，别处可用），只是**不接进助手流程**。

**文档层现状（2026-10-10 复核）**：Hindsight 服务**已在跑**（`localhost:8888` 返回 200）。
现有 6 个 bank，**全部是给需求流水线用的，没有一个是给助手用的**：
`iho-nurse-manager-ui` / `febot-project` / `iho-aers-web` / `iho-cssd-ui` / `li-expertise` / `smoke-test`。

另外，现有 hindsight 调用（`scripts/hindsight-memo.py`、`xiaoqian-manager/lib/server/hindsight/client.ts`）
**全是「软降级」**——服务挂掉时静默返回空、不报错。这在流水线里是优点（不阻塞），但对助手是**陷阱**：
服务一旦没起，你会以为一直在存，其实什么都没存。所以 `/assistant status`（显式报在线状态）是必需项，不是锦上添花。

## 1. 形态与目标（已拍板）

- **形态：只做 Claude Code 内。** 一个 skill（入口）+ 一个（可选）subagent + Hindsight 文档层。
  不起 Web 服务。和现有 `/pipeline` 工作流同构。
- **定位：助手，不是导师。** 三条职责，**零主动性**：

  | 职责                                       | 触发                         | 行为                                              |
  | ------------------------------------------ | ---------------------------- | ------------------------------------------------- |
  | **① 协助开发捋业务**                       | 用户提问（项目/模块/文件夹） | 查索引器 + 文档层，**用人话直接答**               |
  | **② 存文档**                               | **用户明说「存」**           | 存进 Hindsight，带上溯源元数据                    |
  | **③ 解答对外的问题**（**预留，本期不做**） | 别人问这个项目               | 同一套机制：查 → 直接答（未来换入口即可，见 §11） |

- **明确不做（这是与旧「导师」框架的根本区别）：**
  - 不主动发起话题、不主动讲解
  - 不「先问后讲」、不追问、不考试式提问
  - 不自动判定「哪些是业务知识」、不自动入库、不事后抽查提醒
  - 答不上时**直接说答不上**，不追问用户、不兜圈子

**成功判据（唯一）**：第二次问同一个模块，助手能直接引用第一次存的结论，**不必重读代码**，且比第一次更准、更全。

## 2. 总体架构与两条铁律

```
                     /assistant <仓|模块|问题>          ← 入口 skill（服务协议）
                                  │
        ┌─────────────────────────┼─────────────────────────┐
        ▼                         ▼                         ▼
┌───────────────┐        ┌─────────────────┐       ┌──────────────────┐
│ 事实层(现算)   │        │ 助手层(新写)      │       │ 文档层(按需存)    │
│ xiaoyou-      │        │ 服务协议：        │       │ Hindsight :8888  │
│ code-indexer  │        │ 问什么答什么       │       │ assistant-<repo> │
│ v2 · 12 CLI   │        │ 答不上就说答不上   │       │ assistant-shared │
│ + 9 MCP 工具  │        │ 说存才存          │       │                  │
│ 纯静态·不喂LLM │        │ 不主动·不追问      │       │ retain/recall/   │
│ 结果每次现算   │        │                  │       │ list/delete      │
└───────────────┘        └─────────────────┘       └──────────────────┘
        │                         │                         │
        └─────── 事实：代码里读得出来的 ──┴── 文档：代码里读不出来的 ──┘
```

### 2.1 铁律一：事实每次现算，文档只存「读不出来的」

> 路由表、组件树、API 清单会随代码变 → 一律走索引器现算，**不入库**。
> 只有「为什么这么设计 / 这个字段的业务含义 / 这个命名背后的黑话」才值得存。
> 这与 `hindsight-接入方案.md` §5.1「写"为什么"，不写"是什么"」完全一致。
>
> 索引器自己也守同一条纪律：解析不出的一律**带原因 + evidence** 输出（`unresolvedFns[].reason`、
> `dynamic-routes`、`dynamic-storage-key`、`alias.unresolved`……），不静默丢弃。
> 助手拿到「说不清」结果就**照实说说不清**，不脑补。典型如权限：索引器会给出
> `definedInRepo: false`（判定实现在 qiankun 宿主仓）——这正是「为什么这里找不到权限实现」的答案，
> 属于**值得让用户 store 进文档层**的业务知识。

### 2.2 铁律二：对用户只说人话，不摆代码逻辑（重要）

> **助手答给用户的是「业务答案」，不是「代码导读」。**

用户是懂技术的，但**不该被迫读代码来理解业务**。把 `if/else` 分支、函数调用链、生命周期钩子、
变量名和类型签名堆在对话里，既难看又没讲清「这东西到底干嘛的」。

**❌ 不要这样答**

- 贴大段代码块当答案正文
- 用代码执行流程（"先调 A，A 里判断 B，B 命中就走 C"）来组织答案
- 堆砌变量名、类型、API 签名、组件名

**✅ 要这样答**（用大白话回答「这东西是干嘛的」）

| 讲什么                 | 怎么说                                                  | 反例（别这样）                             |
| ---------------------- | ------------------------------------------------------- | ------------------------------------------ |
| **做了什么**           | 这个页面/模块是干什么的，用户在界面上看到什么、能做什么 | "它渲染了 XxxTable 组件并监听 curTab 变化" |
| **有什么参数控制**     | 有哪些开关/选项/配置会影响它的行为，用业务语言          | "props 传了 type 和 mode 两个字段"         |
| **做了什么校验**       | 有哪些限制/必填/报错，**以及为什么这么限制**            | "这里有个 `if (!form.id) return`"          |
| **数据从哪来、到哪去** | 业务口径：谁产生、存哪、谁看                            | "调了 `/icis/api/xxx/search`"              |
| **边界与坑**           | 什么情况下会不灵、容易踩什么坑                          | "动态组件是 `defineAsyncComponent` 挂的"   |

**语言要求**：直白、口语、少术语；术语第一次出现要解释；能说「这个按钮是干嘛的」，
就绝不说「这个 handler 做了什么」。

**代码出处怎么放**：答案仍需 `evidence`（`文件:行`）作为依据，但它是**"我为什么敢这么说"的证据，
不是答案本身**——附在末尾或折叠处，不挡在正文前面。用户想深挖时再展开。

## 4. Bank 与文档模型

### 4.1 Bank 划分

| bank_id                        | 存什么                                                        | 例子                                   |
| ------------------------------ | ------------------------------------------------------------- | -------------------------------------- |
| `assistant-<repo>`（每仓一个） | 该仓的业务知识、模块职责、术语、坑、历史决策                  | `assistant-iho-icis-ui`                |
| `assistant-shared`             | **跨仓通用**：公司业务黑话与缩写、组织/角色含义、通用架构约定 | `mdm`=主数据、`icis`/`cssd` 是什么系统 |

> **与现有 bank 分开**：`li-expertise`（人工评审口味）、`febot-project`（流水线约束）是**研发流程**记忆；
> `assistant-*` 是**业务知识**记忆。混在一起会互相污染检索。

### 4.2 存什么（触发条件 = 用户明说「存」）

> **助手不自己判断该不该存。** 只有你说「存一下 / 存进 X 仓」，它才存。
> 下面两张表不是「自动扫描规则」，而是**你让它存时，它帮你判断「这条值不值得存、该怎么存」的参考**。

**✅ 值得存（代码里读不出来的业务知识）**

| 类别                    | 判据               | 真实例子（来自 iho-icis-ui 实测）          |
| ----------------------- | ------------------ | ------------------------------------------ |
| 业务规则及**原因**      | 为什么这么设计     | 「这个校验为什么放前端」                   |
| 字段/命名的**业务含义** | 标识符 ≠ 字面意思  | `bizType` 实际是订单来源                   |
| **命名不一致映射**      | 三个名字对不上     | `catheter` ↔ `conduit-manage` ↔ "导管管理" |
| 状态机/流程的业务语义   | 业务态 vs 技术态   | 「出科」vs「转科患者」                     |
| 角色/权限的业务含义     | 谁能做什么、为什么 | 权限码背后的角色                           |
| 历史决策与坑            | 为什么不用 X       | 「为什么这个组件是间接引用」               |
| 领域黑话/缩写           | 字面不可解         | `mdm`、`fdp-api`、`ai-generate`            |

**❌ 不值得存（会过期，或代码直接可读）**

| 类别                              | 为什么                       |
| --------------------------------- | ---------------------------- |
| 路由表 / 组件树 / API 清单 / 端点 | 每次用索引器现算，存了必过期 |
| 框架用法、通用编程知识            | 不是本公司的业务             |
| **无 `evidence` 的猜测**          | 直接丢弃，不许入库           |

**每条 retain 的溯源信息必须带**：`repo` / `module` / `evidence=<文件:行>` / `source` / `date`。

> ⚠️ **本节原写法（把上面这行塞进 `context` 字符串）已被实测推翻（2026-10-10）**：
> 一条 retain 会落成 **2 条**（原始条 + 派生条），而 `context`/`metadata` **只有原始条有**，派生条上恒为空；
> `context` 本身还时有时无。**正确通道**是：
> `tags` 写 `repo:` / `module:` / `ev:<文件:行>`（唯一两条都在、且服务端可筛），
> `metadata` 写完整结构（逐字存活，recall 回传，与 tags 冗余一份），`date` 用原生 `timestamp` 字段。
> 证据与做法见 `docs/assistant-agent-实施步骤.md` §附录「实测修订」。

> `confidence` 可选：默认 `high`（你口述即高）；仅当你自己说「这个不确定」时标 `low`。
> 不再有「自动判定置信度」这一说。

### 4.3 三层粒度 → 三种手段

| 粒度       | 手段                                                                                                                                                                    | 成本         | 入 Hindsight 吗                                       |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------ | ----------------------------------------------------- |
| **项目**   | `xiaoyou-index map <仓>`                                                                                                                                                | 极低（静态） | 只存"人讲出来的业务总结"，不存索引本身                |
| **模块**   | `xiaoyou-index trace <仓> <模块>`（一次给出路由→组件树→API→store/事件/权限/存储全链）；追问数据流向用 `trace-state`、事件上下游用 `trace-event`、跨模块关系用 `modules` | 低           | 模块业务职责、边界、坑                                |
| **文件夹** | 助手**按需 `Read`** 该文件夹源码（必要时先 `trace` 缩小范围）                                                                                                           | 低           | **不落派生文档**；值得留的由用户 `store` 进 Hindsight |

### 4.4 Hindsight 可用能力（2026-10-10 从 `/openapi.json` 实测）

清理机制（§P3）**不再有"端点可能不存在"的风险**——所需端点全部存在：

| 端点                                                                | 用途                                                                |
| ------------------------------------------------------------------- | ------------------------------------------------------------------- |
| `GET  .../{bank}/memories/list`                                     | **列出记忆** → `/assistant list` 翻看                               |
| `GET  .../{bank}/memories/{id}` · `PATCH` 同路径                    | 读单条 / **改单条** → 修正已存条目                                  |
| `DELETE .../{bank}/memories` · `.../memories/{id}/observations`     | **删除** → 清理                                                     |
| `POST .../{bank}/memories/dry-run-extract`                          | **干跑抽取，不写入** → 试存形状而不污染 bank                        |
| `POST .../{bank}/health/llm` · `GET .../{bank}/stats`               | `/assistant status` 的健康检查与条目数                              |
| `GET  .../{bank}/tags` · `GET .../{bank}/entities` · `.../graph`    | 元数据与实体图，见下方待验证项                                      |
| `POST .../{bank}/mental-models` · `.../consolidate` · `.../reflect` | 常驻心智模型与复盘（`hindsight-接入方案.md` §5.2 所述能力确实存在） |

**两个待 P0 验证的设计优化（2026-10-10 已验完）**：

1. ~~`tags` 可能优于"把元数据塞进 context 字符串"~~ → **证实**：tags 服务端可过滤，
   `/assistant list --repo X` / `recall --module M` 直接由服务端筛；但 `tags_match` **必须显式传 `all_strict`**，
   默认 `any` 会把无标签条目一起捞出来。据此已把元数据通道从 `context` 改为 `tags` + `metadata`（§4.2）。
2. ~~`dry-run-extract` 可用来试存形状~~ → **未采用**：既然 P0 探针已把真实形状坐实
   （落 2 条 / metadata 只在原始条 / tags 两条都在），干跑就不再必要，徒增一次 LLM 开销。
   接口仍在，需要时可用。

## 6. 端到端验收标准（P4 收口）

1. `/assistant iho-icis-ui` 能出中文项目地图，模块业务名齐全（label 缺的如实标「待补」）。
2. 问「导管管理是干嘛的」→ 能讲清它做什么、有什么参数、数据从哪来到哪去，**用人话，不贴大段代码**。
3. 问数据流类问题（「这个 store 字段谁改的」「这个事件谁发的」）→ 用 `trace-state` / `trace-event` 现算回答，不读大段源码。
4. 问一个不知道的 → **直接说"不知道"**，不追问、不编造、不兜圈子。
5. 说「把这条存进 iho-icis-ui」→ 存进去；**新开会话**再问同一模块 → 直接引用上次结论，且更全。
6. `/assistant list` 能列出已存条目；删掉一条后不再被召回。
7. Hindsight 停掉时，`/assistant` 仍能答题（事实层现算），且**明确提示"文档层不可用"**而非静默。
8. **全程零追问**：助手不反问用户、不"先问后讲"、不生成要用户回答的问题清单。
9. **答案正文通篇是业务语言，无大段代码块**（铁律二）；代码出处只作依据附在末尾。

## 7. 边界：明确不做的事

延续仓库既有哲学，这些是硬边界：

- **不 push、不改目标仓源码**——只读目标仓，产物只写 `docs/assistant/`。
- **不把源码批量喂 LLM**——事实走索引器静态层；对话中允许按需 `Read` 少量文件补行号。
- **敏感文件排除**：`.env*`、`token.temp`、`~/.ssh/*`、`~/.aws/*`；路径白名单校验。
- **不与流水线 bank 混用**：`li-expertise` / `febot-project` 是研发流程记忆，别往里写业务知识。
- **不自动入库**：只有用户明说才存（与旧「导师」框架的关键分界）。
- **不做 Web UI**（本次形态已定为 Claude Code 内）。
- **对外窗口（Web / 钉钉等平台）本期不做**——只在架构上留口子（见 §11），不实现、不排期。
